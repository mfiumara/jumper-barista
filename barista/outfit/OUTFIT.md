# Jumper Barista outfit: Dapper Tricolore (A2b)

Mattia picked **Concept C, Dapper Tricolore**, "as is" (outfit gate `t_bae58085`:
"Outfit = Concept C, Dapper Tricolore (CONCEPTS.md @711e027), as is."). This directory now
builds that one outfit into the model. Concepts A and B stay in `concepts.py` only as the
record of the gate. Everything here is MuJoCo simulation; the real robot has never worn it.

## What it is

The geometry is the A2a concept geometry verbatim (`concepts.py`, `CONCEPTS[C]`), with one
change that `CONCEPTS.md` asked for.

| Part | Geoms (on `upper_shell_link`) | Colour |
|---|---|---|
| Straw trilby | `outfit_hat_brim` (cylinder), `outfit_hat_crown` (cylinder), `outfit_hat_crown_top` (ellipsoid) | straw `#DBBD80` |
| Tricolore band | `outfit_band_verde`, `outfit_band_bianco`, `outfit_band_rosso` (cylinders) | `#008C45`, `#F5F5F0`, `#CC1C2B` |
| Pencil moustache | `outfit_tache_l`, `outfit_tache_l_r` (flush ellipsoid decals, **0.3 mm proud**; it was 0.8 mm in the concept) | espresso-black `#120D0A` |
| Bar towel | `outfit_towel_top`, `outfit_towel_back`, `outfit_towel_stripe` (rigid boxes, rear-right) | cream `#EDE3CC`, stripe `#CC1C2B` |
| White barista jacket | recolour of `base_link_visual` | `#F5F5F0` |

The red shell, legs and claws stay stock. The eye panel in front of `display_module_link`
stays free (`concepts.FACE_BOX`, no intrusions).

## Display-only

Every outfit geom has `contype=0`, `conaffinity=0`, `density=0` and visual group 2. It sits
on `upper_shell_link`, which, like every Jumper body, carries an explicit `<inertial>`, so
the compiler takes no mass or inertia from geoms. The robot's `CollisionCfg` only matches its
named collision meshes, so nothing re-enables collision on the outfit. The jacket recolour
changes `rgba` only. Nothing hangs, swings or uses cloth.

- `tests/test_barista_outfit.py` asserts that body masses, inertias, inertial frames and
  subtree masses are bit-identical with and without the outfit, that the outfit geoms are
  non-colliding and that every stock geom keeps its collision bits. It also checks that a
  400-step drop onto the robot's own contacts is bit-identical, that the eye panel stays
  free, that the decal is at most 0.3 mm proud, and that the committed overrides file is
  current.
- `outfit_check.py m4` runs the **unmodified** `barista/verification/run_m4.py` with the
  outfit applied, and `outfit_check.py compare` compares the result byte for byte with a
  stock run and with the accepted M4 replay.

## How to use it

```python
from outfit import apply, installed, add_to_spec   # barista/outfit/outfit.py
apply(env_cfg)            # dress the robot entity of an mjlab env config
with installed(): ...     # every tasks.load_env_cfg() in the block returns a dressed robot
add_to_spec(spec)         # dress a bare robot MjSpec (tasks.jumper.common.constants.get_spec)
```

`dapper_tricolore.visual_overrides.json` is the same outfit as a portable display-only
description: the geoms in the `upper_shell_link` frame plus the recolour. It is generated by
`outfit.write_visual_overrides`, and a test keeps it in sync.

## Reproduce

```sh
python barista/outfit/outfit_check.py m4 --out <m4_dressed>          # ~85 min under load
python barista/verification/run_m4.py --out <m4_stock> --save-render-states
python barista/outfit/outfit_check.py compare --stock <m4_stock> --dressed <m4_dressed> \
    --accepted-qpos 7adf1e8e12e2e37bfe8c0a794b6ec1b47d7cc7d21fd83589332c8dac4f233f81 --out cmp.json
python barista/outfit/outfit_check.py rollout --out <rollouts>      # brazilian dance + jump policies
python barista/outfit/outfit_check.py clearance --replay <m4_dressed> --rollouts <rollouts> --out clearance.json
python barista/outfit/outfit_check.py render --replay <m4_dressed> --rollouts <rollouts> --out <renders>
```

The renders are front three-quarter, left side and rear three-quarter at the M4 grasp, the
pour pose with the pitcher, a frame of the brazilian dance policy and a jump-policy landing
frame. Each image is labelled as a simulation. Renders are deliverables and are not committed.

## Results (run on 2f090a3's code, 2026-10-11)

**Physics.** The dressed M4 replay is byte-identical to a stock run and to the accepted M4
replay (`cdae494`, qpos `7adf1e8e…`). `motion_substeps.csv` `65a1e623…`, `torque_substeps.csv`
`7c6a39e7…`, `stream_samples.csv` `561a87aa…`, the qpos hash and `render_states.npz` all match,
and `summary.json` matches apart from the commit and output paths. The dressed run passes M4.

**Clearance** (`outfit_check.py clearance`, in mm; "> 30" means never within the 30 mm search):

| Sweep | proud vs claws | proud vs legs | proud vs pitcher | decal vs claws |
|---|---|---|---|---|
| M4 replay, 2850 render frames | > 30 | 23.4 | > 30 | **0.1, intersects (below)** |
| brazilian dance **policy** rollout, 3303 frames at 50 Hz | > 30 | 27.3 | n/a | 19.1 |
| jump **policy** rollout, 700 frames at 200 Hz | > 30 | 19.7 | n/a | > 30 |
| 5 dance references at 50 Hz | > 30 | ≥ 26.2 | n/a | ≥ 6.4 (maze) |
| flat jump reference, native rate | > 30 | 19.7 (towel_back, t = 0.88 s) | n/a | > 30 |

No proud part (hat, band, towel) is ever inside or within 19.7 mm of a claw, leg or the
pitcher. Nothing enters the eye-panel box.

**Known intersection, which is pre-existing.** During the M4 set-down and retreat
(t = 46.18–53.12 s), the stock left claw (`LF_finger_link`, `LF_finger_grip_insert_link`)
passes up to about 10 mm **into the robot's own face** under the sensors. That happens in 315
render frames with or without the outfit, because the M4 motion is unchanged. The left
moustache stroke (`tache_l`) is painted on that patch of face, so the claw also passes
through the decal, in 299 frames. Nearest-neighbour clearance cannot see this (it reports
0.1 mm), so the sweep also tests target samples for being inside each part. That test is
what found it. A2a's "0.1 mm, grazes" was this same penetration.

**Manager disposition (2026-10-12, `t_1e7bda35`, decision c).** Accept the outfit against
the current M4 with this clip window documented; keep the moustache exactly as picked.
The claw-through-face is a real pre-existing M4 self-collision, not an outfit defect.
Its retreat fix belongs to the existing M4R lane (`t_2c59bb36`), not a duplicate outfit
or motion card. **The final film must use the fixed retreat**; hiding the clip by camera
choice is not the resolution. This exception does not assert collision-free current M4
motion or approve an unreviewed M4R candidate. The hash-identity evidence above remains
against the accepted old M4; final integration must revalidate the outfit with the reviewed
fixed motion. No geometry or motion was changed for this disposition.

## `.skin` export: not produced

The design tooling (jumper-design `918d192857fcea1678c2a40b339501004a94d838`,
`shellflow assemble` + `export-skin`, read in `src/shellflow/simulation.py` and
`skin_package.py`) packages one replacement **upper-shell STL** whose per-face colours come
from a Bambu AMS `.3mf` with **at most four palette slots** (`colors_from_ams`: "This adapter
supports one to four palette slots"). Dapper Tricolore needs seven colours on the shell
(straw, verde, bianco, rosso, cream, espresso, plus the stock red shell). A `.skin/3` would
therefore drop or merge colours (the green band at least), which contradicts the pick "as
is". Its packaged shell also has to pass the CAD seam check against the stock shell in
engineering millimetres. Train has no `.skin` loader in any case (`docs/WORKFLOWS.md`,
"Current integration boundaries"). The outfit therefore stays on the `visual_overrides`
path: `outfit.py` plus the JSON above. If a `.skin` is ever needed for the jumper-design web
platform, it is a separate card, and it needs either a richer colour adapter or a reduced
palette that Mattia approves.
